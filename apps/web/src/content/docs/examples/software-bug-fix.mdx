This is the second story on [What is cyber-truss](/cyber-truss/what-is-cyber-truss/): a
problem found in the code and fixed there, with everything around it left behind.

## The system

A web application with a paginated list.

| Artifact-set | Holds |
| --- | --- |
| `{PRD}` | The product requirements for the list feature |
| `{spec}` | The feature specification: intent and criteria for pagination |
| `{code, test}` | The pagination implementation and its tests, one unit of change |
| `{user docs}` | The help page describing how the list pages |
| `{mockups}` | The design mockups, including the page indicator |

Connections:

- `{PRD}` to `{spec}`
- `{spec}` to `{code, test}`
- `{spec}` to `{user docs}`
- `{spec}` to `{mockups}`
- `{mockups}` to `{code, test}`

The last connection exists because the mockups constrain the rendered list in ways the
spec does not state, such as how the page indicator looks. On that edge `{mockups}` is the
[specification](/cyber-truss/model/specification/#specifies-is-a-relation-not-a-layer) of
`{code, test}`. Without it, a mockup could disagree with the code and no connection would
be strained.

## Workflows

| Workflow | Input | Owned | Output | Shape |
| --- | --- | --- | --- | --- |
| Feature delivery | none | `{PRD}`, `{spec}`, `{code, test}` | none | chain |
| Docs update | `{spec}` | `{user docs}` | none | one link |
| Design update | `{spec}` | `{mockups}` | none | one link |
| Design implementation | `{mockups}` | `{code, test}` | none | one link |

Every set here can be revised in place, so every write is to an
[owned](/cyber-truss/model/workflow/#three-roles) set and nothing is an output. Feature
delivery starts at `{PRD}` and owns every set it spans. The other three each read one set
and own one, so
[direction lives in the workflow](/cyber-truss/model/workflow/#direction-lives-in-the-workflow):
design implementation can derive code from the mockups, and it can never change the mockups.

## The change

When the item count is an exact multiple of the page size, the list shows an extra empty
last page. A developer notices, changes the page-count calculation to round up, and
commits. The diff touches the code only.

## Variant A: the spec states the wrong rule

The spec's criteria say the page count is the item count divided by the page size, rounded
down, plus one. That rule is the bug.

### Expected run

1. **Lift.** The change touches `{code, test}`.
2. **Find candidates.** Two workflows own `{code, test}`, so both are
   [upstream candidates](/cyber-truss/model/workflow/#a-change-finds-its-candidates):
   feature delivery and design implementation. No workflow reads `{code, test}`, so there
   are no downstream candidates.
3. **Distill.** Distillation
   [reads back](/cyber-truss/model/canonical-execution/#distillation-reads-backward) along
   each upstream candidate's shape. Along feature delivery it reaches `{spec}`, which states
   *round down, plus one*. The change contradicts that rule, so the walk stops there. Along
   design implementation it reaches `{mockups}`, whose page indicator shows the empty last
   page. Intent: *every page shows at least one item, and the last page shows whatever
   remains.*
4. **Derive criteria.** The page count is the item count divided by the page size, rounded
   up. An exact multiple produces no empty page. An empty list shows one page with an empty
   state, not zero pages. These are version 1 of the run's criteria.
5. **Select**, by the [six steps](/cyber-truss/model/workflow/#how-workflows-are-selected).
   - *Check strain.* `{spec}` contradicts the first criterion and says nothing of the
     third, which is [missing](/cyber-truss/model/connections/#missing), so feature
     delivery is strained. `{mockups}` contradicts the second, so design implementation is
     strained too. The walk found `{mockups}` strained, and design update owns it, so design
     update is selected as well.
   - *Wait on inputs.* Design implementation reads `{mockups}`, which is strained, so it
     waits for design update. Design update reads `{spec}`, which is strained, so it waits
     for feature delivery. Feature delivery has no inputs and starts.
6. **Replay.** Feature delivery translates the intent into a Request at its starting point,
   `{PRD}`. The PRD is too coarse to hold a page-count rule, so the Request
   [passes through](/cyber-truss/model/workflow/#a-replay-starts-at-the-workflows-start)
   to `{spec}`, which amends its criteria, and code and tests are derived. The amended
   `{spec}` is a change of its own. Docs update and design update read it, so both are
   downstream candidates. `{user docs}` states the old page count, so docs update runs.
   Design update was already waiting on this input, and now amends the page indicator.
   When design implementation's input settles, `{mockups}` to `{code, test}` already holds,
   so its replay changes nothing.
7. **Compare.** The developer's fix matches on exact multiples. It does not handle the
   empty list, which the criteria name and the fix never considered. The comparison
   reports an improvement to the change.

Waiting fixes when each workflow can start, not the
[order work arrives in](/cyber-truss/model/canonical-execution/#order-is-not-controlled).
If a designer took a week over the page indicator, design implementation would wait a
week. Feature delivery and design implementation both write `{code, test}` against the
same version 1 criteria, so their writes
[join](/cyber-truss/model/join/#join-and-connection) at the code's
[controller](/cyber-truss/model/controller/#the-join-happens-at-the-controller).

### Settled state

- `{PRD}` is unchanged. It never stated a page-count rule.
- `{spec}` states the round-up rule and the empty-list case.
- `{code, test}` implements both, with tests for an exact multiple and an empty list.
- `{user docs}` and `{mockups}` match the spec.

### Status: Holds

Every order settles in the same state. Each set that has to change is owned by one workflow
that can reach it, and every workflow derives against the same version 1 criteria, adding
nothing the Request did not ask for. If the design review returned a new design, the
workflows would disagree and further cycles would run, and those are bounded by
[the rules that make cycles come to rest](/cyber-truss/model/canonical-execution/#cycles-must-come-to-rest).

The replay spent for nothing in the earlier reading is gone: design implementation waits,
and runs against a settled input. One small point is left unsaid. A workflow whose strain
clears while it waits should check strain again before it replays. The model implies this
and does not state it.

## Variant B: the spec says nothing about the boundary

The spec's criteria never mention how the page count is calculated.

### Expected run

1. **Lift.** The change touches `{code, test}`.
2. **Find candidates.** The same two upstream candidates as variant A, and no downstream
   ones.
3. **Distill.** Along feature delivery, `{spec}` neither holds nor contradicts the change,
   so the walk continues to `{PRD}`, the workflow's declared start, which is too coarse to
   hold a page-count rule. Along design implementation, `{mockups}` depicts a list that is
   not an exact multiple and has no place for a page-count rule. The intent is the same as
   in variant A.
4. **Derive criteria.** The same as variant A.
5. **Select.** `{spec}` states none of the criteria, so all three are
   [missing](/cyber-truss/model/connections/#missing), and feature delivery is strained.
   `{mockups}` has no place for a page-count rule, the same judgement that passes a Request
   through a PRD, so design implementation is not strained and nothing is waiting.
6. **Replay.** Feature delivery passes through `{PRD}`. `{spec}` gains the round-up rule
   and the empty-list case, and code and tests are derived. The amended spec has two
   downstream candidates. `{user docs}` contradicts the new page count, so docs update
   runs. `{mockups}` shows no exact multiple and still meets the spec, so design update
   does not.
7. **Compare.** The same as variant A: the fix misses the empty list, and the comparison
   reports the improvement.

The mockups do not decide the outcome. If a mockup happens to depict an exact multiple, the
run follows variant A, and design update amends the drawing once the spec is amended.
Either way the rule lands in the spec, because missing strain comes from the change's
criteria, not from what a drawing depicts.

### Settled state

The same as variant A.

### Status: Holds

Missing strain gives the intent a home. The status rests on two judgements. The criteria
are derived by distillation, so an unstable distillation produces unstable missing strain.
And that `{mockups}` has no place for a page-count rule is a call about
[levels](/cyber-truss/model/specification/#specifications-exist-at-every-level), which the
model has not said how to make across artifact types.

## What it tests

- [Candidates](/cyber-truss/model/workflow/#a-change-finds-its-candidates) found by
  lookup. Both variants find the same two upstream candidates. The amended spec finds docs
  update and design update downstream, with nothing having to notice the docs first.
- [Missing strain](/cyber-truss/model/connections/#missing). Variant B was a gap until the
  kind existed. Strain-only selection found nothing, because the spec stated no rule the
  fix could break.
- The contradiction case. In variant A the code contradicts a rule `{spec}` states, across
  two units of change. Which kind of strain that is
  [remains open](/cyber-truss/model/open-questions/#which-strain-does-an-implementation-that-contradicts-its-specification-leave).
- [Distillation reads backward](/cyber-truss/model/canonical-execution/#distillation-reads-backward)
  along a workflow with no inputs. Feature delivery owns everything it spans, and the walk
  follows its shape back toward `{PRD}`.
- [How workflows are selected](/cyber-truss/model/workflow/#how-workflows-are-selected).
  Design update is reached because the walk found `{mockups}` strained, and design
  implementation waits on its strained input instead of replaying against it.
- [Direction lives in the workflow](/cyber-truss/model/workflow/#direction-lives-in-the-workflow).
  Design implementation reads the mockups, so the page indicator can only change through
  the spec and design update.
- [Criteria derived before the replay](/cyber-truss/model/canonical-execution/#criteria-are-derived-before-the-replay-not-after).
  The empty-list case comes from the criteria, not from the fix.
- A triangle of connections. `{spec}` reaches `{code, test}` directly and through
  `{mockups}`, so two workflows own the same code, and their writes join at one controller.
- [A replay starts at the workflow's start](/cyber-truss/model/workflow/#a-replay-starts-at-the-workflows-start).
  Feature delivery visits `{PRD}` and passes through it, and the settled state leaves the
  PRD unchanged.
- Obligations and tickets. The what-is story mentions a ticket that was never opened. In
  the [workflow catalog](/cyber-truss/model/workflows/) a follow-up ticket is how a team
  records an obligation, not an artifact-set, so this example leaves it out.
